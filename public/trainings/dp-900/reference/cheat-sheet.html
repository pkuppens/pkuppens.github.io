Domain 1 · Core data concepts 25–30%

Structured data
Fixed schema of rows and columns — the shape a relational table enforces. Example: a Customers table.
Semi-structured data
Self-describing data with tags or keys but no rigid table schema — JSON, XML, key-value pairs.
Unstructured data
No predefined model — images, audio, video, PDFs, free text. Typically lands in Blob storage.
Row-based file formats (CSV / TSV / JSON / XML)
Human-readable, good for interchange and small/medium data.
Columnar file formats (Parquet / Avro / ORC)
Binary, compressed, column-pruning — built for large-scale analytics reads. Contrast: row-based formats above.
OLTP (transactional)
Online Transaction Processing: many small, fast reads/writes on current data; normalized; ACID-compliant. Runs the business.
OLAP (analytical)
Online Analytical Processing: large aggregate queries over historical data; denormalized (star schema); read-optimized. Reports on the business.
ACID
Atomicity, Consistency, Isolation, Durability — the transaction guarantees that make relational OLTP systems trusted with money.
Data roles
Database administrator keeps a database available, performant, secure, backed up; data engineer builds pipelines that move and shape data; data analyst models and visualizes data for insight.

Domain 2 · Relational data on Azure 20–25%

Normalization
Structuring tables to remove redundancy so each fact is stored once — prevents update anomalies, at the cost of more joins on read.
Primary key / foreign key
A primary key uniquely identifies a row; a foreign key references a primary key in another table to enforce a relationship.
SQL statement families
DDL defines structure (CREATE, ALTER, DROP); DML manipulates data (SELECT, INSERT, UPDATE, DELETE); DCL controls access (GRANT, REVOKE).
Database objects
View = a saved query used like a table; stored procedure = saved executable SQL; index = a structure that speeds lookups.
Azure SQL Database
Fully managed PaaS relational database (single database or elastic pool). Least administration — the default choice for a new cloud-native app. Contrast: SQL Managed Instance, SQL on VM.
Azure SQL Managed Instance
PaaS with near-100% SQL Server engine compatibility (SQL Agent, cross-database queries) — the lift-and-shift target for on-prem SQL Server.
SQL Server on Azure VMs
IaaS: you run full SQL Server on a VM you manage — maximum control, most administration. Use when you need OS-level access or a feature PaaS lacks.
Azure Database for MySQL / PostgreSQL / MariaDB
Managed PaaS for the popular open-source relational engines — pick the one matching your existing app/engine.

Domain 3 · Non-relational data on Azure 15–20%

Azure Blob storage
Object storage for unstructured data (files, images, backups, data-lake content). Contrast: Files = mountable filesystem, Table = key-value.
Blob access tiers (Hot / Cool / Cold / Archive)
Colder = cheaper to store, slower/costlier to read. Archive must be rehydrated before reading.
Azure Files
Fully managed file shares over SMB/NFS, mountable like a network drive.
Azure Table storage
Schemaless key-value / NoSQL store for huge volumes of structured, non-relational data, keyed by partition + row key. Cheap and simple.
Azure Queue storage
App-to-app messaging queue — the fourth Azure Storage service. Not a data store you'd pick for structured/unstructured data itself; a frequent wrong-answer option next to Blob/Files/Table.
Azure NetApp Files / Azure Disk
Filesystem/volume storage, not object storage — common distractors against Blob storage on "which service is designed for unstructured objects" questions.
Azure Cosmos DB
Globally distributed, multi-model NoSQL database with single-digit-millisecond latency and multi-region writes. Reach for it when an app must be global, elastic, and low-latency (IoT, retail, gaming).
Cosmos DB APIs
Choose by data model / migration source: NoSQL (Core) for documents (native default for new apps), MongoDB, Cassandra (column-family), Table (key-value), Gremlin (graph).

Domain 4 · Analytics workload on Azure 25–30%

ETL vs. ELT
ETL transforms data before loading (in a staging engine); ELT loads raw first, then transforms in the target (lake/warehouse) using its own compute. ELT suits big-data lakes.
Data warehouse
A relational analytical store holding cleaned, structured, modelled data (star schema) for BI/reporting. Schema-on-write.
Data lake
Low-cost storage for raw data of any structure at scale (built on Blob/ADLS). Schema-on-read. Contrast: warehouse = schema-on-write, structured.
Lakehouse
Combines a data lake's cheap raw storage with warehouse-style structure/queries — the model Microsoft Fabric and Databricks promote.
Azure Databricks
An Apache Spark–based analytics platform on Azure for large-scale data engineering, data science, and ML.
Microsoft Fabric
Microsoft's unified, SaaS analytics platform — data integration, engineering, warehousing, real-time intelligence, and Power BI over one OneLake.
OneLake
The single, tenant-wide lake storage layer that every Microsoft Fabric workload reads and writes to — one copy of data, shared across engines.
Azure Data Factory
Azure's data integration/orchestration service for building ETL/ELT pipelines — moves and transforms data at scale. Not a report-authoring or analytics-engine tool (a common quiz distractor against Power BI Desktop and Databricks).
Batch vs. streaming
Batch processes bounded data collected over time, on a schedule (high latency, high throughput); streaming processes unbounded events as they arrive (low latency, near real time).
Azure Stream Analytics
Microsoft's managed real-time analytics engine for processing streaming event data as it arrives.
Fabric Real-Time Intelligence
The Microsoft Fabric workload for streaming/real-time analytics — the Fabric-native alternative to Stream Analytics.
Power BI
Microsoft's BI/visualization tool: author in Power BI Desktop, publish to the Power BI service, share reports (multi-page, detailed) and dashboards (single-page, pinned tiles).
Power BI data model
The tables, relationships, and measures (calculated aggregations) a report is built on — the analyst's semantic layer.
Choosing a visualization
Trend over time → line chart. Composition/share of a whole → pie or stacked bar. Value vs. target → KPI visual. Values by geography → map. Correlation between two measures → scatter chart.

The recurring exam traps

Near-miss pairs the exam loves to test
  • OLTP (current, normalized, many small writes) vs. OLAP (historical, denormalized, large aggregate reads).
  • ETL (transform before load) vs. ELT (transform after load, in the target).
  • Data warehouse (schema-on-write, structured) vs. data lake (schema-on-read, raw, any structure).
  • Blob storage (objects) vs. Azure Files (mountable share) vs. Table storage (key-value) vs. Queue storage (messaging, not a data-modeling choice).
  • Batch (scheduled, bounded) vs. streaming (continuous, unbounded, low latency).
  • Azure SQL Database (least admin, new app) vs. SQL Managed Instance (near-full compatibility, lift-and-shift) vs. SQL Server on a VM (full IaaS control).
  • Azure Databricks (Spark engineering/ML platform) vs. Microsoft Fabric (unified SaaS suite over OneLake) vs. Power BI (visualization layer only).
  • Report (multi-page, detailed, built in Power BI Desktop) vs. dashboard (single page of pinned tiles).
